# J2: running Test262's basics, in five steps

J2 makes SilverJS run code (docs/design.md section 3): values, the
heap and its collector, handles, strings and objects, the register
bytecode compiler and interpreter, functions and closures, exceptions,
strict mode, the budget, the heap limit, and the core built-ins.
Target: 35% of Test262's measured set run to completion as it says.
Every decision is the design note's; this page orders the work. Each
step lands with its tests, a sabotage pass, the gate and a push, as J1
did.

**Measured as it grows** (the lead, 2026-11-20). The design's bet is a
heap in safe Rust, named by indices. From the step that runs code, a
micro-bench set (silver-work/tooling/silverjs-bench: property get and
set on one shape and on four, calls, closures, a numeric loop, array
push and index, string concatenation, allocation churn) runs at every
step against QuickJS-ng, with the bytes a plain object takes. A core
operation more than 3x slower than QuickJS-ng is raised with the lead
before anything is built on it. QuickJS-ng's numbers at the start: 160
to 810 ms per bench, 121 to 137 bytes per `{a, b}` object.

**J2.1 Values and the heap.** The NaN-boxed `Value` (section 1.3):
doubles as themselves, int32, the singletons, and references as 32-bit
indices, every double from bytes canonicalized. Typed arenas of fixed
cells, each with a generation; an `Agent` owning them, with its id and
heap limit. The collector: precise mark-sweep, marking with a stack of
its own, sweeping lazily, a heap verifier after each collection in
debug builds. Handles: `Scope` and `Local` tied by lifetimes, `Global`
and `Weak` checking generation and agent on every use, in release too.
The `gc-stress` feature. Tests hold a collection to keeping exactly
what is rooted.

**J2.2 Strings, symbols and objects.** Flat Latin-1 and UTF-16
strings with cached hashes; atoms for property keys, integer keys kept
apart; symbols. Ordinary objects in dictionary mode (shapes are J6),
with attributes, and the spec's internal methods (`[[Get]]`, `[[Set]]`,
`[[DefineOwnProperty]]`, `[[Delete]]`, `[[OwnPropertyKeys]]`) over the
prototype chain; arrays with packed, holey and sparse elements.
From here the micro-bench reports bytes per object.

**J2.3 The compiler.** Its walks over the tree are bound as the
parser's are (the lead, 2026-11-20): by the same stack budget from
compile entry, or iterative, tested on a synthesized source nested as
deep as the deepest real bundle met (275 levels, a minified bundle of the
web engine's sweep corpus), so that a source the parser accepts is never
refused by the compiler first. Scope analysis over J1's tree, iterative:
each binding a register, or a slot of an environment when a closure
captures it or `eval` or `with` can reach it. Bytecode for the register
machine with an accumulator, 8-bit operands with wide prefixes,
inline-cache slot numbers reserved, source positions. The compiled
unit holds no heap reference: constants, scope descriptors, positions.
A disassembler, for the tests.

As landed (`src/compiler/`): functions are compiled from a list in the
order the analysis met them, never by recursion, so nesting functions
costs the compiler no stack; within a function, the chains the parser
builds in loops are walked with a stack of the compiler's own, and the
rest recurses where the parser did, under the same budget. Measured to
the parser's own limit (about 970 levels) on three shapes (functions
inside functions, expressions alone, statements alone), the compiler
takes at most 26% of the stack the parser took in release builds, 52%
in debug. A unit validator checks every operand, jump and handler; the
tests run it on every unit they make. What J3 adds (classes,
generators, `async`, destructuring, spread, iterators and `for-of`,
tagged templates) and modules (J5) are refused by name for now, as
`CompileError::Unsupported`. Two simplifications wait for J3: a
function's parameters share its body's scope (the spec gives parameter
expressions a scope of their own), and Annex B's function declarations
in blocks are not also hoisted as `var`s.

**J2.4 The interpreter.** Frames on the agent's register file, not
Rust's stack; calls, returns and closures; `try`, `catch`, `finally`
and throw; the step budget, charged at backward jumps and calls, and
termination that runs no `catch` or `finally`; the re-entry count for
natives. The micro-bench runs on SilverJS from here. The errors the
interpreter throws are worded as the reference browser words them,
from one message table (design note, section 1.11).

As landed (`src/interp/`): frames on the agent's register file, one
loop for script calling script, a nested run bounded by a re-entry
count (256) for natives calling script, 10,000 frames before a
RangeError, unwinding by each function's handler table, the budget's
hook terminating past every handler. Environments and for-in iterators
are internal cells; functions keep their code and environment in the
object's side box. A minimal realm (the core and error prototypes, the
global object, `Array.prototype.push`, `Object.prototype.toString` and
`valueOf`, `Error.prototype.toString`) runs the micro-benches; the rest
is J2.5's, as are mapped `arguments` (an unmapped object until then),
primitive wrapper objects, `Error.prototype.stack`, and a stack frame's
column at `new`. Micro-bench ratios against QuickJS-ng: 1.9x to 2.75x,
but string concatenation at 60x for want of ropes, which J2.4b brings
forward from J6 (the lead, 2026-11-20). `Agent::heap_stats` reads in
constant time, with `committed` beside `bytes`.

**J2.4b String building.** Brought forward and changed by the lead's
rulings of 2026-11-20: shared two-ended buffers rather than rope nodes,
since a capped rope depth with an eager flatten makes appending
quadratic (design note, section 1.3). Tested by bytes copied, linear at
two sizes for appending, prepending, both alternating and right-leaning
concatenation; by two strings extending one prefix; by a 10 MB build
dropped while its first window is kept; and under `gc-stress`. String
concatenation runs at 1.29x QuickJS-ng's time (60x before); branching off
one prefix in a loop is the known gap, J6's.

**J2.5 The core built-ins and Test262 execution.** `Object`,
`Function`, the `Error` family, `Array` (the basics), `String`,
`Number`, `Boolean`, `Symbol`, `globalThis`, by an embedding API of
natives. The Test262 runner runs tests: harness includes, `$262`'s
basics, `async` tests' `$DONE`, negative runtime tests, with an
expectations file of its own. The fuzz targets `silverjs_run` and
`silverjs_gc`. Section 1.11's surface: `Error.prototype.stack` in the
reference browser's format (with `eval` and `new Function` frames),
`Error.captureStackTrace`, `prepareStackTrace` and `stackTraceLimit`,
`Function.prototype.toString` for natives, bound functions and
classes, and the built-ins' own keys in its order, each pinned by a
test of Chrome's observed output.

In three steps, each with its sabotage pass and push (2026-11-21):
J2.5a the built-ins, the embedder's natives and the runner's execution;
J2.5b the stack (`Error.prototype.stack`'s format with its `eval` and
`new Function` frames, `captureStackTrace`, `prepareStackTrace`,
`stackTraceLimit`, the column at `new`) and direct `eval`, whose frames
the stack shows; J2.5c several realms in an agent (`$262.createRealm`)
and the fuzz targets `silverjs_run` and `silverjs_gc`.

As landed, J2.5a (`src/builtins/`): natives are named by a table and an
index, each intrinsic's own properties a table installed in its order,
which is the reference browser's (two probes of Chrome 157, pinned by
`builtins_tests`; the names a later step brings are listed there). A
native is given its receiver, its arguments on the register file and
`new.target`; a bound function is unwrapped before the call, script or
native. The embedder's natives are Rust closures
(`Scope::native_function`), with `get_property`, `set_property`, `call`
and `eval_script` giving back what script threw; the Test262 runner and
`examples/shell.rs` use that API and nothing else. Wrapper objects (a
`String` one exotic, its one-unit strings from a table the heap keeps),
mapped `arguments` (each mapped index reads and writes its parameter's
slot), `Reflect`, `Math`, the URI functions and `escape`, beyond the
list above. `Function.prototype.caller` and `arguments` are the
reference browser's own accessors, null for a sloppy function, not
`%ThrowTypeError%` (docs/chrome-surface.md). What waits for an iterator
protocol (`Array.prototype.values` and `@@iterator`, `Object.fromEntries`,
`Math.sumPrecise`), for RegExp (`match`, `search`) and for the
normalization tables (`normalize`) is left to those steps. Test262
run, the whole measured set in under two minutes: 17,238 of 47,526
(36.27%) run to completion as they say, 40.17% without Temporal, past
J2's 35%. The failures are, by count, the syntax J3 compiles (classes,
generators, `for-of`, destructuring, `async`), the built-ins of later
steps (Date, typed arrays, Promise, Map, JSON, Proxy, RegExp,
iterators), modules (J5), Annex B's functions in blocks (J3), and the
four tests of `%ThrowTypeError%` as `caller`'s accessor, which the
reference browser does not follow (`chrome-surface`). Fixed on the way:
`for (x in o)` with a plain name on its left threw "Invalid left-hand
side" (a J2.3 bug).

As landed, J2.5b (`src/builtins/stack.rs`, `src/interp/eval.rs`): an
error's frames are captured when it is made (the function frames and,
kept beside them, the natives'), and formatted when `stack` is first
read; every column was checked against Chrome 157's answers to a probe
page of 46 cases SilverJS wrote (42 match; class syntax and JSON wait
for J3 and J4, and a stack overflow's column is recorded as not
followed). Positions gained a column of their own beside the text an
error message quotes. Direct `eval` compiles its code as a unit of its
own whose undeclared names are looked up by name; a sloppy one's `var`s
and functions are made in its caller's variable environment first, a
function's kept in an object of extra bindings on that environment.
Indirect `eval` goes the same way, its `var`s deletable. Environments
now know their `const` and named-function slots, so an assignment by
name throws, or does nothing, as the binding wants.

**Right after J2.5: the parser's frames.** Real bundles nest to 275
levels at 1.0 to 2.6 KiB of stack a level in release builds, 92% of the
384 KiB default budget, and parse at 20 to 33 MB/s where Test262's
large files reach 76 to 144. Tokens of about 130 bytes cloned in hot
paths and large results returned by value cost both; shrinking them
widens the margin and closes some of the speed gap. The default stays
384 KiB until then: past it a source is refused with a SyntaxError,
never a crash. Silver Browser passes a larger budget from J5.

**Risks.** A bounds check on every heap access (the bench measures
it); rooting bugs, which the generations, the verifier and
`gc-stress` exist to find; a compiler and interpreter large enough to
want splitting further, which happens as each step lands, not by
building ahead.
